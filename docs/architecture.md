# Архитектура CommerceCore API

## Структура и зависимости

Приложение — асинхронный модульный монолит FastAPI. Все маршруты имеют префикс
`/api/v1`. Модули `auth`, `users`, `catalog`, `cart` и `orders` сгруппированы по
предметным областям. Внутри модуля маршруты обрабатывают HTTP, Pydantic-схемы
проверяют данные, сервисы содержат бизнес-правила, а репозитории обращаются к базе.
ORM-модели и ограничения описывают структуру хранения. Общие настройки, подключения,
безопасность и обработчики ошибок находятся в `app/core`.

PostgreSQL — основной источник данных. SQLAlchemy работает с ней асинхронно через
asyncpg; схема изменяется отдельными миграциями Alembic. Redis подключается асинхронным
клиентом и участвует в проверке готовности. При завершении приложения соединения
закрываются. Сейчас Redis не используется для кэширования или хранения данных каталога.

Настройки читаются из переменных окружения и `.env`. Соединения создаются в жизненном
цикле приложения; каждая операция с базой получает сессию через зависимость FastAPI.
Ошибки предметной области централизованно преобразуются в HTTP-ответы. Клиентам не
выдаются подробности SQL-ошибок; ошибки валидации не содержат исходные значения полей.
Журнал приложения выводится в JSON: для HTTP-запросов записываются шаблон маршрута,
метод, статус и длительность, для ошибок базы — тип ошибки без SQL и параметров.
Заголовки, тела запросов, значения параметров пути и строки запроса не включаются в
эти записи. Стандартный access-журнал Uvicorn отключён, так как он содержит сырой URL.
Для необработанных HTTP-ошибок журнал сохраняет тип исключения, но убирает сообщение
исключения и traceback из записи Uvicorn: они могут содержать секретные данные.

## Пользователи и доступ

Публичная регистрация создаёт только `customer`. Пароли хешируются Argon2, а
вычисления хеша выполняются вне основного цикла событий. При входе выдаются
подписанные JWT: короткоживущий access-токен и refresh-токен. В базе хранится только
SHA-256-хеш refresh-токена, срок действия и время отзыва.

При обновлении строка refresh-токена блокируется, старый токен отзывается и создаётся
новый в одной транзакции. Выход отзывает переданный refresh-токен; уже выданный
access-токен продолжает действовать до истечения срока, если пользователь активен.
Зависимости FastAPI проверяют токен, актуальность пользователя и роль. Управление
каталогом доступно `admin`, изменение статуса заказа — `admin` и `manager`.
Пользователь видит только собственные заказы и работает только со своей корзиной.
Первого администратора создаёт интерактивный CLI, а не публичный API.

## Каталог и корзина

Категории и товары связаны внешним ключом. Уникальные `slug`, неотрицательные цена
и остаток обеспечиваются ограничениями базы. Цена хранится как `NUMERIC(12,2)` и
обрабатывается через `Decimal`. Публичный API возвращает только активные товары;
удаление товара через API означает деактивацию, поэтому история заказов сохраняется.

На пользователя приходится одна корзина, а на пару корзины и товара — одна позиция.
Добавление проверяет активность товара, но не списывает и не резервирует остаток.
Изменения корзины и оформление заказа используют блокировку строки корзины,
сериализуя эти операции для одного пользователя.

## Оформление заказа и идемпотентность

Клиент передаёт непустой список товаров и количеств, соответствующий корзине, и
заголовок `Idempotency-Key`. Сервер вычисляет SHA-256 от нормализованного списка:
пары UUID и количества сортируются, поэтому порядок позиций не влияет на результат.
Ключ уникален в пределах пользователя.

В одной транзакции сервис:

1. Блокирует корзину и проверяет наличие заказа с переданным ключом.
2. Сверяет состав корзины с запросом и блокирует товары в стабильном порядке UUID
   через `SELECT FOR UPDATE`.
3. Проверяет активность товаров и остатки, вычисляет сумму в `Decimal`.
4. Создаёт заказ и позиции со снимком названия и цены, списывает остатки и очищает
   корзину, затем фиксирует транзакцию.

При ошибке транзакция откатывается. Ограничения базы запрещают отрицательные остатки,
а уникальное ограничение `(user_id, idempotency_key)` дополнительно защищает от
дублирования. Повтор с тем же ключом и списком возвращает прежний заказ с HTTP 200;
повтор с другим списком возвращает HTTP 409. Новый заказ возвращается с HTTP 201.
Для каждого нового намерения оформить заказ нужен новый ключ.

## Статусы и отмена

Разрешены переходы `pending → confirmed`, `pending → cancelled`,
`confirmed → completed` и `confirmed → cancelled`. Статусы `completed` и `cancelled`
терминальные. При отмене сервис блокирует заказ и связанные товары, возвращает
остатки и изменяет статус в одной транзакции. Повторная или конкурентная отмена не
может вернуть остатки дважды: после блокировки проверяется актуальный статус заказа.

## Проверки и развёртывание

Интеграционные тесты используют отдельную PostgreSQL и Redis; для тестов базы
создаются временные базы с применёнными миграциями. Проверяются в том числе конкурентное
оформление, повторные запросы, отмена и права доступа. CI запускает Ruff, миграции,
тесты с порогом покрытия и сборку Docker-образа. Coverage учитывает переключения
SQLAlchemy через greenlet.

Docker Compose запускает API, PostgreSQL и Redis. Приложение в контейнере работает
от непривилегированного пользователя; миграции запускаются отдельной командой.
Инструкции по запуску и тестированию приведены в [README](../README.md).
